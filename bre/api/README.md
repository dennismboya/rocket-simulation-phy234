# BRE scoring API (Phase 5)

The service is the only source of predictions for the dashboard: every number a screen shows
comes from `bre.predict` through these endpoints, no model code lives in the UI, and every
prediction shown is written to `predictions_log` and `audit_log`.

Start it from `bre/`:

```bash
BRE_VENV=/home/user/bre-venv make api            # uvicorn api.main:app on 127.0.0.1:8000
BRE_API_PORT=8010 BRE_VENV=/home/user/bre-venv make api
```

On first start with the default database (`data/synthetic/demo.db`, `BRE_DB_URL` overrides it)
the service seeds the synthetic demo book (60 G_Q investors plus five hand-written archetypes,
`bre.demo`), seeds the five interventions, fits the demo model (Q4, MAP, at most 1500 Adam steps,
`db.demo_seed`) and registers it as the active model; this takes about a minute. Set
`BRE_API_AUTOSEED=0` to refuse to start without an active model instead. `demo_mode` is true
whenever the served model was trained on synthetic data or the database lives under
`data/synthetic/`, and every response then carries `synthetic: true`.

Interactive docs: `http://127.0.0.1:8000/docs`. The committed `openapi.json` is regenerated by
`python api/export_openapi.py` (also run by `make api`), and `tests/test_api.py` fails when it
drifts from `app.openapi()`.

## Endpoints

| Method, path | Purpose |
|---|---|
| `GET /health` | liveness, served model version, `demo_mode` |
| `GET /model` | version, type, metrics, calibrated contexts, provenance (`training_data_refs`, `data/CATALOG.md` entry names), `is_synthetic_training`, the pre-registered decision rule and the evaluation status |
| `GET /clients` | the served book (`client_id`, `display_label`, covariates, response count) |
| `GET /interventions` | the intervention scripts and their context transforms |
| `GET /market` | current market state (cached files unless `BRE_MARKET_NETWORK=1`) and its mapping to a scenario |
| `POST /predict` | one investor, one scenario: predicted probability of selling, 80/95% intervals, interference terms, top driver, calibration counts |
| `POST /profile` | decision-state profile: baseline state, context sensitivities, consistency score, classical-equivalent risk score and its R² against the state angle |
| `POST /score_book` | JSON list of clients + one market state → triage table |
| `POST /score_book/csv` | the same from a CSV upload (multipart) |
| `POST /interventions/rank` | interventions ranked by predicted change in P(sell), each labelled "predicted effect, not causally validated" |

Validation errors return HTTP 422 with the offending field in `detail[].loc`.

Wording: every probability is the *predicted probability of selling* under the served model;
the service never says an investor "will sell". Intervals are percentiles over the artifact's
parameter draws (see `GET /model` → `interval_source`); a context's `n_calibration` is the number
of training responses behind it, and a context with fewer than the documented minimum is marked
`uncalibrated: prior only`.

## Batch scoring: `POST /score_book`

```bash
curl -s -X POST http://127.0.0.1:8000/score_book \
  -H 'Content-Type: application/json' \
  -d '{
    "clients": [
      {"client_id": "DEMO-C01", "display_label": "Demo client 01",
       "covariates": {"age_band": "30-44", "wealth_band": "50-250k", "invest_experience_yrs": 5,
                      "self_reported_risk_tolerance": 3, "financial_literacy_score": 2, "education": "bachelor"}},
      {"client_id": "DEMO-C02", "display_label": "Demo client 02",
       "covariates": {"age_band": "60+", "wealth_band": ">1M", "invest_experience_yrs": 30,
                      "self_reported_risk_tolerance": 5, "financial_literacy_score": 5, "education": "graduate"}}
    ],
    "market_state": {"drawdown_pct": -0.14, "duration_days": 40,
                     "cause_frame": "analysts now expect a recession after weak earnings",
                     "recovery_pct": 0.02, "vix_bucket": "high",
                     "media_intensity": "high", "social_cue_prevalence": "medium"},
    "target": 0.25
  }' | python -m json.tool
```

The CSV form takes the same market state as a form field:

```bash
printf 'client_id,display_label,age_band,wealth_band,invest_experience_yrs,self_reported_risk_tolerance,financial_literacy_score,education\n' > book.csv
printf 'DEMO-C01,Demo client 01,30-44,50-250k,5,3,2,bachelor\n' >> book.csv
curl -s -X POST http://127.0.0.1:8000/score_book/csv \
  -F file=@book.csv \
  -F 'market_state={"drawdown_pct": -0.14, "cause_frame": "recession fears", "social_cue_prevalence": "high"}' \
  -F target=0.25 | python -m json.tool
```

Response: one row per client with `p_sell` (predicted probability of selling under the market
state), `p_baseline` (no loss, no context), `change_vs_baseline`, `ci80_low`/`ci80_high`,
`top_driver` (the context or the loss whose removal changes `p_sell` the most),
`suggested_intervention` (the active intervention with the largest predicted reduction, a
predicted effect that is not causally validated), `drawdown_capacity` (the largest design-grid
loss the client is predicted to sit through under the typical-crisis context before P(sell)
first exceeds `target`), `status` (`stable` < 0.25 ≤ `elevated` < 0.50 ≤ `high`, with
`uncalibrated context` appended when a scenario context has too few training responses),
`known_client` (the client's fitted random effects were used) and `synthetic`. `scenario` says
how the market state was mapped (loss clipped to the design range, cause frame matched to the
nearest calibrated news context with a `weak_match` flag, contexts in order of arrival).

Rows of clients unknown to the database are logged under the reserved client `api:batch` unless
`register_unknown` is true, in which case client rows are created for them. A 300-client book
scores in well under two seconds once the forward passes are warm (the service warms them at
startup; `tests/test_predict.py` prints the timing).
